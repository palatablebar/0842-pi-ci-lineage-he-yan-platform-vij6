# 召回停发登记台

## 定位

批次核验台按整份样例一次性计算；召回停发登记台处理**逐条到达**的批次/合批记录与召回事件。每份记录各查各的、按内容幂等登记，晚到记录触发全量重算。页面入口：`/recall`，数据独立保存在 `RECALL_DB`（默认 `instance/recall.sqlite3`），与批次核验库互不影响。

## 业务口径

1. **每份记录各查各的**：批次记录按 `lot_id` upsert（内容不变不计新版本，内容变化累加版本）；召回事件按 `recall_id` 唯一。
2. **召回闭包**：召回沿血缘上下游双向传播，同一无向连通分量共用上游，分量内批次立即停发，原因码 `CONTAMINATED`。
3. **旁支照常出货**：与问题分量不共享任何上游、且血缘完整的独立分支证实未混入，状态保持 `SHIPPABLE`。
4. **缺父待核**：分量中存在未登记的父批次、无法排除混入时，分量内批次先 `PENDING` 停发，原因码 `ANCESTOR_MISSING`，详情列出缺失父批次；晚到记录补齐后按实际来料重算，可转为正式停发或恢复出货。
5. **问题来料未登记**：召回指向的问题批次本身尚未登记时，生成待核事项 `PROBLEM_LOT_UNREGISTERED`，记录补齐后自动转为闭包停发。
6. **多召回叠加**：停发按 `(批次, 召回)` 唯一存储。一个批次同时受两起召回约束时存在两条停发行；解除一起只释放对应行，另一起仍生效则继续停发，不能恢复出货。
7. **重试幂等**：同一起召回（相同 `recall_id`）的重试登记直接返回既有事件，不新增事件、不新增停发记录。不同召回误用相同 `event_id` 返回 `EVENT_CONFLICT`。
8. **审计轨迹**：解除召回或重算移除约束时，停发行标记为 `RELEASED` 而非删除，可通过 `list_holds(active_only=False)` 追溯。

## 判定与原因码

| 出货状态 | 含义 |
|---|---|
| `SHIPPABLE` | 无任何生效停发约束，照常出货 |
| `PENDING` | 约束均为待核（缺父批次/问题批次未登记），停发待核 |
| `HOLD` | 至少一条正式停发（`CONTAMINATED`），立即停发 |

| 停发原因码 | 触发条件 |
|---|---|
| `CONTAMINATED` | 与问题来料同属一个血缘完整的连通分量 |
| `ANCESTOR_MISSING` | 分量缺父批次记录，无法排除混入 |
| `PROBLEM_LOT_UNREGISTERED` | 召回指向的问题批次记录尚未登记（待核事项） |

## 重算时机

每次批次登记（内容变化时）、召回登记、召回解除后，都基于当前全部批次记录与未解除召回重算：

- 无向连通分量来自 `parent_lot` 投料边（`L4:200;L5:40` 语法，单父可省略贡献量）。
- 血缘完整性递归判定：批次自身及全部祖先记录均已到齐才算完整；环不影响判定。
- 待核与正式停发在重算中互相转换，不需要人工改状态。
